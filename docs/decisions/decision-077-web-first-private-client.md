# decision-077 — MultiTracker: web-first клиент и границы приватности

Статус: accepted

Backlog Decision: decision-077

Backlog Document: doc-178

Уточняет пользовательский выбор: decision-075 — приватность прежде автоматической синхронизации, ключи только у пользователя

Исследование: [privacy-and-stack.md](../research/privacy-and-stack.md)

## Context

Пользователь хочет сначала кликабельный интерфейс для телефона и компьютера, затем приложение, где серверный оператор не может прочитать инвестиционные записи. Для production выбраны ручные операции и импорт файлов, ключ только у пользователя; автоматическая синхронизация ждёт решения о локальном соединителе. Позднее запрос на полный демонстрационный интерфейс расширил экраны: макет включает формы подключения/API, синхронизации, настроек и импорта с имитацией сохранения.

Браузерное шифрование защищает содержимое при утечке базы данных только если ключ не покидает клиента. Веб-сервер при этом контролирует JavaScript, исполняемый в браузере: владелец или атакующий, способный выпустить изменённый код, может снять секрет и открытые данные до/после шифрования. Потерянный единственный ключ означает потерю доступа к резервной копии. Шифротекст не скрывает автоматически время, размер, IP и частоту обращений.

## Decision

1. Первую версию интерфейса строить как адаптивное клиентское React + TypeScript приложение на Vite со статической поставкой. Кликабельный демонстрационный макет показывает расширенный набор экранов, но все данные вымышленные, а сохранение только имитируется локально. В нём нет реальных учётных записей, API-запросов, биржевых секретов или криптографии. SSR не нужен: он не шифрует данные, а передача расшифрованных props/HTML открывает их браузеру.
2. Реальные операции и локальный разбор файлов остаются в браузере; сервер позднее принимает только шифротекст и минимум маршрутизирующих метаданных. Не включать API-ключи бирж, серверный разбор plaintext или фоновую автосинхронизацию до проектирования локального соединителя.
3. Не писать собственные шифры, KDF и протоколы ключей. До реальных данных отдельно утвердить стандартную криптобиблиотеку/браузерный API, формат и версию контейнера, nonce, derivation параметры, lifecycle ключа, recovery и устройство-enrollment; провести независимое крипторевью.
4. Не обещать защиту от оператора, способного заменить сайтовый JavaScript. CSP, отсутствие сторонних скриптов, воспроизводимая сборка и публичные исходники улучшают защиту и проверяемость, но не отменяют эту границу доверия.

## Consequences

- Быстрый макет не привязывает команду к server runtime, БД, Redis или очереди.
- Демо может показывать будущие подключения и настройки, но это не означает наличия их production-поведения или разрешения отправлять реальные секреты.
- Веб-модель сохраняет простой путь к установке как PWA, но нативные возможности не входят в ранний объём.
- Пользователь должен сохранить recovery secret вне сервиса; сброс пароля не восстанавливает зашифрованную историю. Добавление устройства требует явного безопасного способа переноса/повторной упаковки ключа.
- Администратор базы данных не должен видеть активы, площадки, суммы, комиссии или заметки. Требуются проверки отсутствия plaintext в запросах, телеметрии и журналах. Непрозрачные ID и шифротекст уменьшают утечку метаданных, но сами метаданные частоты/объёма остаются.
- Если позднее понадобится SSR или native-first клиент, решение пересматривается по измеренной продуктовой потребности и после повторной проверки границы расшифровки.
