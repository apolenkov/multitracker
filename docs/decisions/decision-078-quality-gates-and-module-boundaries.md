## Context

Проект готовится к открытому выпуску и должен оставаться понятным для человека. Ограничения пользователя: когнитивная сложность не выше 10, файл не длиннее 300 строк, функция не длиннее 50 строк, запрет `let` и изменений объектов/массивов на месте. В то же время чрезмерное разбиение и Onion/DDD слои добавят пустые обёртки до появления реальных границ.

Проверки должны быть исполняемыми в CI, иначе указанные числа превращаются в пожелания. Порог сложности зависит от версии инструмента и правила подсчёта, поэтому конфигурация должна быть закреплена.

## Decision

1. До макета создать только необходимые ворота: ESLint с TypeScript и правилом cognitive complexity ≤ 10; лимиты файла ≤ 300 строк и функции ≤ 50 строк; запрет `let`; запрет переназначения параметров/изменений входных коллекций; TypeScript `strict`; независимые lint, typecheck и production build команды, обязательные для CI.
2. Зафиксировать lockfile и установить PR проверки утечек секретов и уязвимых зависимостей (dependency review/advisories). Не добавлять отдельный Redis, очередь или серверную архитектуру до конкретной фоновой задачи.
3. Начать с четырёх предметных зон без абстрактного слоя: `ui/` (представление), `portfolio/` (чистые финансовые функции), `privacy/` (граница криптоформата и ключей), `import/` (локальный разбор и проверка файла). Добавлять `server/` только при реализации хранения шифротекста.
4. До обработки настоящих персональных данных включить security lint/SAST, secret scanning, тестирование CSP/security headers, файловых лимитов и XSS; проверить контракт, что тестовые имена активов/суммы не попадают до шифрования в HTTP, сервер, журналы, аналитику и crash reports.
5. До публичного репозитория подготовить лицензию, README с моделью угроз и пределом JavaScript-поставки, SECURITY.md, правила вклада и CI. Все security/dependency gates должны завершаться ошибкой на неприемлемом результате; их нельзя ослаблять только ради зелёного CI.

## Consequences

- Макет можно проверять в CI без появления серверных или фоновых компонентов.
- Демо-формы API и синхронизации имитируют сохранение только на фиктивных данных; реальные секреты и сетевые подключения остаются вне демо.
- Чистые функции финансового расчёта проще проверять отдельными примерами и не связывать с браузерными API.
- Небольшое число содержательных папок сохраняет прозрачность; новые слои появляются только когда есть конкретный владелец ответственности.
- Инструментальные версии и определения подсчёта нужно закрепить и описать; пороги сложности/длины являются проектной политикой, а не универсальным стандартом.
- Проверка отсутствия plaintext до шифрования и проверка ключевого recovery остаются обязательными критериями допуска к реальным данным, а не частью демо-макета.
