# decision-094 — эталон v2: профиль F+P1, проверка типов на TypeScript 7, строгие пороги для нового кода

Статус: accepted. Дата: 2026-10-01.

Связанные решения: [decision-078](decision-078-quality-gates-and-module-boundaries.md) (прежние ворота
качества), [decision-083](decision-083-complete-prototype-and-scenario-modules.md) (модули по сценариям),
[decision-093](decision-093-seven-section-scope.md) (семь разделов).

## Контекст

Владелец попросил подтянуть конфигурацию репозитория к эталону v2
(`deep-research-report-v2.md`, лежит вне репозитория; цифры и версии в нём сверены на
1 октября 2026 года). Условие: пороги и правила только добавляются, ничего не
ослабляется; встроенных директив подавления и пропущенных тестов нет; прежние
пороги 300 строк на файл, 50 строк на функцию и 10 ветвлений остаются. Правки в
`src/` и в `scripts/ui-*.ts` по условию задания не вносятся: там параллельно
работают другие исполнители.

Сокращения: ADR (architecture decision record) — запись архитектурного решения;
DDD — предметно-ориентированное проектирование; RC (release candidate) —
кандидат в выпуск; API — программный интерфейс.

## Профиль

Эталон делит проекты на профили по настоящей сложности предметной области. Для
MultiTracker выбраны два:

- **F — фронтенд-приложение.** Это статический макет на React и Vite, без сервера.
  Послойная структура Feature-Sliced Design из профиля F рассчитана на Next.js; здесь
  её не вводим: модули уже разложены по сценариям (decision-083).
- **P1 — приложение с внешними границами.** Чистое ядро расчётов
  (`src/model/portfolio.ts`) и тонкая оболочка из интерфейса. Порты нужны только на
  настоящих внешних границах: файлов, сети, хранилища и ключей. Сейчас настоящих
  границ нет, все данные демонстрационные.

Выше профиль не поднимаем: слои «луковицы» и DDD добавили бы пустые обёртки.

## Решение

### 1. TypeScript 7 для проверки типов, TypeScript 6 рядом

Проверено по первоисточникам на 1 октября 2026 года:

- В npm у пакета `typescript` метка `latest` — 7.0.2 (`npm view typescript dist-tags`).
- У `typescript-eslint` 8.71.0 допустимый диапазон TypeScript — `>=4.8.4 <6.1.0`
  (`npm view typescript-eslint peerDependencies`).
- У TypeScript 7 нет стабильного API компилятора: он обещан в версии 7.1. Задача
  typescript-eslint [#10940](https://github.com/typescript-eslint/typescript-eslint/issues/10940)
  открыта. В ней 24 апреля 2026 года участник команды написал, что без API
  интеграцию не сделать и команда его ждёт.
- Рекомендуемая схема описана в
  [объявлении TypeScript 7.0 RC](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0-rc/)
  от 18 июня 2026 года: имя `typescript` указывает на `@typescript/typescript6`, а
  TypeScript 7 ставится под другим именем.

Совместимость есть и воспроизводится, поэтому внедрено:

- `"typescript": "npm:@typescript/typescript6@6.0.2"` — псевдоним именно с именем
  `typescript`, потому что `typescript-eslint` импортирует пакет по этому имени
  (псевдоним с другим именем он бы не увидел). Приходит TypeScript 6 с командой
  `tsc6`. Оболочка 6.0.2 тянет внутрь компилятор под именем `@typescript/old` с
  диапазоном `^6`; чтобы любая будущая установка не вышла за границу `<6.1.0`, в
  `overrides` он зафиксирован на 6.0.3 (так же репозиторий уже закрепляет
  `deepmerge-ts`). `scripts/check-gates.ts` проверяет, что версия, которую получает
  `typescript-eslint`, начинается с `6.0.`.
- `"typescript-7": "npm:typescript@7.0.2"`.
- `npm run typecheck` запускает TypeScript 7 по пути
  `node node_modules/typescript-7/bin/tsc`. Причина: оба пакета приносят команду
  `tsc`, и после `npm ci` в `node_modules/.bin/tsc` оказалась копия 6.0.3
  (`@typescript/old`). Утверждение объявления «`npx tsc` просто работает с 7.0» в
  этом дереве не подтвердилось, поэтому выбор по имени команды не используется.
- `npm run typecheck:ts6` запускает `tsc6 --noEmit` и входит в `npm run check`:
  код обязан проходить обе версии (требование эталона).
- Шаг `build` теперь вызывает `npm run typecheck`.

Замер на коммите e481428 после установки: TypeScript 7.0.2 и TypeScript 6
завершают проверку всего дерева с кодом 0; `eslint` не выводит предупреждений о
неподдерживаемой версии. Понижения нет: компилятор под `typescript-eslint` прежний,
6.0.3. В запись `package-lock.json` для Linux попал `@typescript/typescript-linux-x64`
(необязательная зависимость для `os: linux`). Проверено в контейнере `node:26`
(OrbStack) на чистой выгрузке коммита: `npm ci`, TypeScript 7.0.2, `tsc6` и `eslint`
завершились с кодом 0.

Условие снятия: когда `typescript-eslint` объявит поддержку TypeScript 7 (задача
#10940), удалить псевдоним, `overrides`, `typecheck:ts6` и запуск по пути.
Задача в бэклоге на слежение за #10940 пока не заведена.

### 2. Строже компилятор и правила, где дерево уже чисто

Добавлено в `tsconfig.json` (ошибок на дереве 0): `noImplicitReturns`,
`noImplicitOverride`, `noUncheckedSideEffectImports`, `allowUnreachableCode: false`,
`allowUnusedLabels: false`. Параметры `isolatedModules` и
`forceConsistentCasingInFileNames` только закрепляют поведение, которое уже
подразумевалось (`verbatimModuleSyntax` и значение по умолчанию); новой строгости в
них нет.

Не добавлено (измерено, ошибок больше нуля):

| Параметр                             | Ошибок | Решение                                                  |
| ------------------------------------ | -----: | -------------------------------------------------------- |
| `noPropertyAccessFromIndexSignature` |     84 | отложено до правки кода                                  |
| `skipLibCheck: false`                |      1 | остаётся `true`: ошибка в типах `@radix-ui/react-select` |

В `eslint.config.ts` вместо `recommendedTypeChecked` подключены
`strictTypeChecked` (он включает прежний набор) и `stylisticTypeChecked`, плюс:

- `switch-exhaustiveness-check`, `return-await: always`, `prefer-readonly`,
  `consistent-type-assertions` со стилем «никогда», `max-depth` 2 — на дереве
  нарушений 0;
- `restrict-template-expressions` в строгом виде с одним послаблением,
  `allowNumber: true`. До этой записи правило стояло с мягкими параметрами по
  умолчанию, поэтому это усиление; на дереве осталось 2 нарушения в
  `scripts/ui-smoke-negative.ts` (раздел 4);
- `no-confusing-void-expression` с `ignoreArrowShorthand: true`. Без параметра
  правило давало 143 нарушения (стрелка-однострочник в обработчиках React), с
  параметром 0; правило раньше не стояло;
- для `src/**`: запрет `process.env`, `Date.now()`, `new Date()` без аргументов,
  `Math.random()`, `crypto.randomUUID()`;
- везде: запрет `export *`. В скриптах проверок и конфигурации время и переменные
  среды читать разрешено: они не часть приложения.

Сводка «до и после» получена сравнением эффективных наборов правил
(`eslint --print-config`) для десяти путей: ни одно правило уровня «ошибка» не
стало слабее; у части изменились только параметры, и все изменения — усиления либо
возврат прежних параметров для файлов из списка долга. Число включённых правил
уровня «ошибка» выросло со 127 до 176–178.

Замена устаревшего `tseslint.config` на `defineConfig` из ESLint не удалась:
TypeScript отклоняет тип плагина `eslint-plugin-react-hooks`, а обход потребовал бы
приведения типа, запрещённого правилами. Оставлен `tseslint.config`; файл
`eslint.config.ts` внесён в список долга ниже.

### 3. Пороги 250 / 25 / 8 только для нового кода

Строже общих 300/50/10: файл не длиннее 250 строк, функция — 25 строк, ветвлений и
когнитивной сложности — по 8. Действуют только в `scripts/exhaust/**` и
`tests/exhaust-core.test.ts` (эти файлы появятся из другой ветки; пока файлов нет,
правило безвредно). Параметры повторены целиком: в плоской конфигурации правило с
параметрами заменяет прежние, и без `IIFEs: true` и счёта пустых строк порог молча
стал бы мягче.

Чтобы пустой шаблон путей не прошёл незамеченным, в `scripts/check-gates.ts`
добавлены пары примеров: один и тот же текст нарушает строгий порог по путям нового
кода и не нарушает его по обычному пути. Механически дробить старые функции ради
порога не нужно: эталон прямо считает такое дробление замечанием ревью.

Граница печати ratchet-леджеров в `scripts/exhaust`: печать ловит случайные
правки файлов книги, а намеренный сброс книги остаётся видимым только в кодовом
ревью — технически заблокировать его нельзя.

### 4. Измеренный разрыв и долг

Измерено на коммите e481428, пороги заданы из командной строки `eslint`:

| Правило (порог)                    | Нарушений | Файлов |
| ---------------------------------- | --------: | -----: |
| `max-lines` (250)                  |         5 |      5 |
| `max-lines-per-function` (25)      |       153 |     69 |
| `complexity` (8)                   |        15 |     12 |
| `sonarjs/cognitive-complexity` (8) |         4 |      3 |

Координатор называл 1037, 97 и 37 нарушений (по порядку порогов: файл, функция,
ветвления). В этой рабочей копии цифры другие; причина расхождения не выяснена
(возможно, другое дерево или другой способ счёта): NOT VERIFIED. Решение от них не
зависит: старые пороги остаются, строгие действуют для нового кода.

Не включено из набора эталона, потому что дерево его не проходит (число
нарушений при его параметрах): `explicit-module-boundary-types` — 148,
`strict-boolean-expressions` — 34, `max-params` (3) — 21, `no-console` — 6 (все в
скриптах проверок, которым вывод нужен; в `src` нарушений нет, но пробные примеры
проверок тоже пишут в консоль, поэтому правило не добавлено), `max-nested-callbacks`
— 1. Эти правила войдут по одному, по мере правки кода, а не разом.

Явный долг: десять нарушений в девяти файлах. Правка кода по условию задания
запрещена, поэтому в `eslint.config.ts` под каждое правило свой блок только с
файлами, где оно нарушается:

| Правило | Что сделано | Файлы |
| --- | --- | --- |
| `no-deprecated` (раньше не стояло) | отключено | `eslint.config.ts`, `src/demo/connection-form.tsx`, `src/forms/EntityDialog.tsx`, `src/forms/OperationForm.tsx` |
| `no-unnecessary-condition` (раньше не стояло) | отключено | `src/Dialog.tsx`, `scripts/ui-smoke-dialogs.ts` |
| `prefer-regexp-exec` (раньше не стояло) | отключено | `scripts/ui-smoke-report.ts`, `scripts/ui-smoke.ts` |
| `restrict-plus-operands` (стояло) | прежние мягкие параметры, не выключено | `scripts/ui-smoke-geometry.ts` |
| `restrict-template-expressions` (стояло) | прежние мягкие параметры, не выключено | `scripts/ui-smoke-negative.ts` |

Для правил, которые уже действовали, послаблений нет: файл остаётся под прежней
проверкой. Новые файлы под список не попадают; исправленный файл вычёркивается.
Это долг, а не отмена правил.

Не измерено: правило именования логических переменных (`naming-convention`):
NOT VERIFIED.

## Условие перехода к P2 и P3

Профиль повышается отдельной ADR с наблюдаемой причиной. Признаки перехода от P1
к P2 (четыре кольца, правило зависимостей в автоматической проверке с
отрицательными примерами):

- в макет приходят настоящие данные: файлы, ключи, шифрованное хранилище на
  сервере, настоящие подключения к бирже (пункт 4 decision-078);
- ошибка вызвана протечкой внешнего слоя в правила расчёта либо правила расчёта
  нельзя проверить без браузера или сети;
- одно изменение правила требует правок во многих местах (размножение правок).

Признаки перехода к P3 (ограниченные контексты и предметный язык): несколько
подобластей, где один термин значит разное (например, портфель у биржи и у
владельца), и несколько команд. Пока ничего из этого не наблюдается.

## Последствия

- `npm run check` дополнительно проверяет TypeScript 6 и строгие правила. Замер
  полного прогона: около 32 секунд до изменений, около 37 секунд после (одиночные
  замеры на одной машине).
- Параллельные исполнители правят `src/` и `scripts/ui-*.ts`: новые нарушения
  строгих правил в новых файлах теперь блокируют их слияние.
- Список долга в `eslint.config.ts` — к исправлению; из него файлы только
  вычёркиваются.
- Псевдоним TypeScript 6 и запуск TypeScript 7 по пути временные; условие снятия
  описано в разделе 1.
- Облачная автоматическая проверка на `ubuntu-latest` не запускалась: ничего не
  отправлялось в GitHub. Контейнерный прогон на `node:26` её не заменяет; его
  архитектура процессора не сверялась с x64 облака: NOT VERIFIED.
