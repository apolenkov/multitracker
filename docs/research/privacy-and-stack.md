# MultiTracker: приватность и начальный стек

Исследование по официальным спецификациям и документации, проверено 2026-09-30. Это архитектурная рекомендация, не описание уже реализованного продукта. Выбранное направление: сначала приватность, ручные операции и импорт файлов; ключ доступен только пользователю; автоматическая синхронизация ждёт решения о локальном соединителе.

## Вывод

Для первого макета достаточно адаптивного React + TypeScript приложения на Vite, собранного как статический сайт. Оно должно быть кликабельным, но работать на синтетических данных в памяти. PWA можно добавить после согласования нужного офлайн-поведения. После макета следует проверить модель угроз и протокол шифрования отдельно, прежде чем хранить реальные записи. Сервер получает и сохраняет только шифротекст; расшифровка, ручной ввод и разбор импортируемого файла происходят в браузере.

Шифрование в браузере действительно может скрыть содержимое от оператора БД и обычных серверных API. Оно не скрывает его от владельца сайта, способного заменить доставляемый JavaScript: подменённый код может украсть пароль или данные до шифрования. Это предел обещания приватности, его нужно показывать пользователю простым языком. [Web Crypto API](https://www.w3.org/TR/WebCryptoAPI/) задаёт браузерные криптопримитивы; [OWASP Cryptographic Storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html) требует исходить из модели угроз и планировать управление ключами.

## Угроза и границы

| Кто атакует / что теряется | Что может дать клиентское шифрование | Что остаётся открытым или не решается |
|---|---|---|
| Читатель резервной копии, администратор БД или утечка БД | При корректном клиентском шифровании содержимое операции и портфеля остаётся шифротекстом | Время, объём и частота записи, связь строк с аккаунтом, IP и факт использования сервиса; если метаданные хранятся отдельными колонками — также их значения |
| Сервер приложения / его администратор | БД и API не получают ключ в нормальном протоколе | Сервер контролирует исходники и может поставить JavaScript, который снимает мастер-пароль, импорт, расшифрованные данные или ввод. CSP уменьшает риск части XSS/инъекций, но не защищает от самого издателя, который меняет приложение |
| XSS, вредоносная зависимость, расширение браузера, заражённое устройство | CSP, отсутствие сторонних скриптов и короткая активная сессия сокращают поверхность | Код, уже исполняющийся в доверенном origin, видит открытый текст и может инициировать расшифровку. Защита устройства — отдельная граница |
| Потеря пароля/ключа | Зашифрованные резервные копии не раскрываются | Без отдельно сохранённого recovery key сервер не может восстановить содержимое. Сброс учётной записи не должен обещать восстановление старых данных |
| Импорт через API биржи | В выбранном первом срезе API-ключи не принимаются вовсе | Даже read-only ключ может раскрыть балансы, сделки и историю. При утечке он действует до отзыва и согласно выставленным разрешениям; не отправлять его в браузерный SaaS или в логи |

**Управление ключом (проектное решение для проверки):** не использовать пароль пользователя напрямую как ключ данных. Сгенерировать случайный ключ данных, шифровать им записи и упаковать ключ данных ключом, выведенным из секрета пользователя стандартной KDF. Секрет/recovery-код показывается только пользователю при настройке; в базу уходит только зашифрованный ключ данных. Утеря секрета означает необратимую потерю расшифровки. Для второго устройства пользователь переносит секрет через явно подтверждённый защищённый процесс; облачное автовосстановление и тихое добавление устройства в первый срез не включать. Это только форма протокола для threat-model review, а не готовая спецификация криптографии.

Не писать свои шифры, KDF, форматы ключей или криптографический протокол. Использовать стандартный Web Crypto API либо библиотеку с внешним аудитом после отдельной проверки. Для аутентифицированного шифрования пригоден стандарт AES-GCM при соблюдении уникальности nonce; повтор nonce с тем же ключом опасен. Параметры KDF, версия формата, лимиты попыток, хранение ключа в памяти и удаление состояния при блокировке должны быть выбраны и испытаны отдельно. `extractable: false` ограничивает экспорт CryptoKey, но не защищает от вредоносного кода, который попросит браузер использовать ключ.

**Метаданные и журналирование:** в незашифрованной части оставить только нужные для маршрутизации поля с непрозрачными случайными идентификаторами и шифротекстом. Не хранить в открытом виде символ, площадку, сумму, валюту, заметку или имя портфеля; не строить по ним серверные индексы. Размеры и моменты доступа всё равно могут коррелировать с активностью. В журналах фиксировать события входа, отказа, импорта и администратора без тела запроса, ключей, паролей, сессионных идентификаторов, CSV-строк и расшифрованных объектов. [OWASP Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) перечисляет секреты и идентификаторы сессий как данные, которые нужно исключать или маскировать.

**Ручной импорт:** принять CSV/XLSX-файл через браузер, проверить тип/размер/заголовки/числовую точность, разбирать локально и показывать предварительный просмотр. Не посылать исходный файл на сервер и не писать его значения в телеметрию или аварийные отчёты. После подтверждения сформировать зашифрованные записи. API-ключи и OAuth-доступы не нужны для ручного импорта и поэтому отсутствуют в первом срезе. Если локальный коннектор появится позже, он должен хранить ключи у пользователя, иметь только чтение, минимально необходимые разрешения и возможность быстро отозвать ключ. Документация площадок показывает, что разрешения бывают раздельными и могут включать перевод/вывод; например, [Bybit API key info](https://bybit-exchange.github.io/docs/v5/user/apikey-info) перечисляет разрешения кошелька и IP-привязку, а [Kraken API key info](https://docs.kraken.com/api/docs/rest-api/get-api-key-info) явно различает запрос балансов и вывод средств.

**JavaScript, CSP и поставка:** ограничить скрипты строгой CSP по nonce/hash, запретить `unsafe-inline`/`unsafe-eval`, не встраивать сторонние рекламные/аналитические скрипты и тестировать политику в браузере. CSP — дополнительная защита от инъекций, а не гарантия от скомпрометированного издателя. Для сервиса, который обещает приватность от оператора, независимая воспроизводимая поставка и проверяемое открытое происхождение клиентского кода повышают проверяемость, но сами по себе не гарантируют, что пользователь запустил именно проверенный артефакт. См. [OWASP CSP Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Content_Security_Policy_Cheat_Sheet.html).

## Стек и порядок

| Вариант | Что даёт | Цена / ограничение | Решение |
|---|---|---|---|
| React + TypeScript + Vite | Быстрый клиентский макет, прямой DOM/CSS, статическая поставка, нет обязательного серверного слоя | API, хранение и серверные операции надо будет добавить отдельной границей | **Сейчас.** Лучший прямой путь к кликабельному адаптивному web/PWA прототипу |
| Next.js | Маршрутизация, серверный рендеринг и серверные компоненты | Дополнительный серверный рантайм и границы сериализации. SSR не является шифрованием: переданный клиенту prop уже открыт клиенту; он также не мешает серверу подменить JS | Отложить, если появится реальная потребность в SSR/серверных функциях. [Документация Next](https://nextjs.org/docs/app/guides/data-security) отдельно предупреждает, что переданные Client Component данные доступны клиенту |
| Expo / React Native Web | Общая React Native кодовая база для native и web | Это не обычный HTML/CSS React: web использует React Native Web, есть различия API и поведения; ради одной web-first формы добавляет платформенные ограничения | Выбирать, только если нативные приложения станут ближайшей целью. [Expo FAQ](https://docs.expo.dev/faq/) описывает отличия React Native от React DOM |
| PostgreSQL | Надёжное постоянное хранение пользователей, зашифрованных объектов, схемы, транзакций | RLS помогает разделять строки пользователей, но администратор БД/superuser обходит защиту; RLS не заменяет шифрование | Позже, когда понадобятся аккаунты, зашифрованная синхронизация/архив и серверное управление пользователями. [PostgreSQL Row Security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html) |
| Redis / очередь | Кэш с TTL, rate limiting, фоновые задачи, ограниченный поток работы | Ещё один сервис и отказная поверхность; очередь дублирует задачу, если нет реального фонового потребителя | Не включать в прототип и стартовый backend. Добавить при измеренной нужде в фоновой обработке/лимитировании. Для MVP биржевых API не требуется |

SSR может выдавать оболочку HTML и сервером отрисованный публичный интерфейс. Это не меняет место расшифровки: приватный ключ и plaintext должны оставаться в клиентском контексте, а серверные данные, переданные как props/HTML, открыты браузеру. Для прототипа SSR не даёт нужного преимущества.

## Простые границы модулей

Не вводить Onion/DDD слои ради названий. Держать четыре понятных зоны:

1. `ui/`: страницы, формы и адаптивная навигация; только отображение и события.
2. `portfolio/`: чистые TypeScript функции для ручных операций, валют, комиссий и расчёта результата в валюте отчёта; без IO. Доменная арифметика должна отдельно определить валюту покупки, комиссию, обменный курс и правило стоимости/прибыли до реальных данных.
3. `privacy/`: браузерный фасад для ключей, шифрования/расшифрования и формата зашифрованного объекта. На макете заменён синтетическими данными, никаких крипто-обещаний в макете.
4. `import/`: локальный парсер CSV/XLSX, проверки, preview и конвертация в тип операции; импортный путь не делает сетевых запросов.

Позже отдельный `server/` обслуживает только аккаунт, передачу ciphertext, журнал безопасности и очереди при их появлении. SQL схема содержит opaque user/object IDs, crypto format version, nonce, ciphertext и минимум нужных метаданных. Любой plaintext-индекс или серверный отчёт требует пересмотра обещания приватности.

## Проверяемые ворота

| Проверка | Критерий | Сейчас / позже |
|---|---|---|
| Сложность | Когнитивная сложность каждого изменённого метода/функции ≤ 10 (выбрать один линтер/плагин и проверять в CI) | Сейчас; на каждом PR |
| Размер | Файл ≤ 300 строк; функция ≤ 50 строк; CI завершает сборку ошибкой при превышении | Сейчас |
| Стиль мутаций | Запретить `let` через ESLint; не менять входные аргументы, общие объекты и массивы на месте; `const` и копии для изменений | Сейчас; при реализации доменной логики |
| Типы и сборка | TypeScript strict, typecheck отдельно от build, lint отдельно от форматирования; весь набор обязателен в CI | Сейчас |
| Безопасность кода | SAST/security lint, проверка секретов, security headers/CSP тест, проверка небезопасной загрузки файлов, проверка XSS | Макет: secret scan/CSP baseline; продукт: полный набор и review криптопротокола |
| Зависимости | Lockfile обязателен, минимальный набор зависимостей, автоматические vulnerability alerts и dependency review на PR, запрет неразрешённых high/critical уязвимостей | Сейчас |
| Данные | Тест-контракт: тестовая строка актива/суммы/заметки не попадает в HTTP body, БД, логи, аналитику и crash report до шифрования; потеря recovery key документирована и проверена | Прототип — только мок; перед реальными данными обязателен |
| Импорт | Fixture-файл проходит только локальный parse/preview; malformed и чрезмерно большие файлы отклоняются с безопасной ошибкой; нулевые строки данных никуда не отправляются | При первом функциональном срезе |
| Open source и CI | Лицензия, README с threat model/границами приватности, SECURITY.md, CONTRIBUTING.md, CODE_OF_CONDUCT.md, шаблон issue/PR; CI проверяет lint/types/build, тестовые контракты, секреты, зависимости | README и лицензия — до публичного репозитория; остальные — до первого внешнего вклада |

Числовые пределы сложности и размера — политика команды, а не универсальные стандарты: закрепить версии инструментов/плагинов и точное правило подсчёта, иначе порог не воспроизводим. Не ослаблять gate ради зелёного CI; слишком сложную функцию надо упростить или осознанно пересмотреть порог.

## Путь от макета к первому защищённому срезу

1. Кликовый адаптивный макет на Vite/React/TypeScript: portfolio chooser, объединённый обзор, операции, импорт с локальным preview, выбор валюты отчёта и языковые строки. Только вымышленные данные, без аккаунтов, API и криптографии.
2. Уточнить расчёт инвестиционного результата (денежные потоки, комиссии, валютные курсы и метод себестоимости) отдельными примерами и согласовать с пользователем; без этого «профит» будет вводить в заблуждение.
3. Утвердить threat model и протокол ключа: создание/восстановление/добавление устройства/закрытие сессии, форматы ciphertext, nonce, KDF и версионирование. Провести независимое крипторевью до хранения реальных операций.
4. Ввести ручные операции и локальный импорт; клиент сначала шифрует подтверждённые записи. Добавить серверное хранение только ciphertext, учётные записи и проверки разграничения доступа.
5. Отдельно принять решение о локальном коннекторе. До этого нет автоматического опроса брокера, передачи API-секретов и Redis-очередей синхронизации.
