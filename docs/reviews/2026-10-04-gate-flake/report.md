## Причины (две независимые, обе доказаны артефактами прогона)

### 1. Ожидание маршрута проходило до коммита раздела

`location.hash` меняется синхронно при клике по ссылке, а DOM раздела —
следующим коммитом React. Все ожидания вида
`location.hash === '#route' && !!document.querySelector('#main h1')`
(`sweep.ts navClick`, `walk-reach.ts goTo`, `trusted.ts restore`,
`run.ts openApp`, `matrix-actions.ts hashWait`, `axis-pass.ts`,
`envctl.ts`, `ui-smoke.ts navigate`, `ui-smoke-context.ts
restoreNavigation`) принимали `h1` ПРЕЖНЕГО раздела за признак готовности.

Доказательство из журнала падающего прогона
(`clicks.jsonl` прогона `muszwman-101358`):

- 5 из 7 записей навигации имеют `stateBefore === stateAfter` —
  `overview`, `portfolios`, `history`, `import`, `sync` (у `connections`
  и `settings` хеши различаются: рендер успевал отставать на один раздел).
  Переход `#import` (seq=395): `ia00xk → ia00xk` — hash уже новый, DOM
  ещё страницы «Операции».
- Все 188 «пропущенных» сигнатур `import|-|` — это пути DOM раздела
  «Операции» (select фильтра портфеля, кнопка добавления, раскрытие
  фильтров, 12 карточек записей), посчитанные с меткой `import`.
  Перечисление и часть обхода снялись с чужого раздела, элементы
  остались непокрытыми → `missing` в реестре, который обязан быть
  точным снимком принятого непокрытия (ratchet).
- Доля пропусков у границы: sweep `465/1164 = 0.399` при лимите `0.4` —
  те же гонки давали `walk:unreachable dialog#record-edit-dialog` и
  `trusted`-пропуски, но класс `missing` ронял прогон первым.

Внутристраничный обход имел ту же форму гонки: `clickPath` восстанавливал
`location.hash` и ждал один кадр (`settle`, ≤50 мс) — следующие кандидаты
могли быть сняты с чужого раздела; `reopen` объявлял диалог недоступным по
снимку одного кадра, если коммит `showModal` ещё не долетел.

### 2. DemoModal терял повторное открытие при схлопнутом батче React

`src/demo/modal.tsx` открывал `dialog` только в эффекте монтирования
(`useEffect(..., [])`). Последовательность smoke-аудита
`Escape → клик по открывателю` даёт два обновления состояния
`open:false` (из `onClose`) и `open:true` (из клика). На быстром хосте они
коммитятся по отдельности: размонтирование + монтирование, эффект
срабатывает, `showModal` вызывается. На загруженном хосте React успевает
схлопнуть оба обновления в ОДИН коммит: компонент не перемонтируется,
эффект не перезапускается, `dialog` остаётся `open=false` при
`open:true` — кнопка-открыватель умирает до смены раздела. `wait --fn`
в `waitOpen` ждал открытия до таймаута (~30 с), отсюда 382 с прогона.
Это дефект продукта, а не теста: реальный пользователь, нажавший Escape и
быстро кликнувший «Сравнить версии», получал мёртвую кнопку навсегда.

Проверена и исключена гипотеза pointer-guard (src/dialog-pointer-guard.ts):
окно 500 мс гаснет любым `keydown`/`input`/`change` — Escape перед
повторным кликом снимает все вооружённые окна, блокировать повторный клик
нечему.

## Что изменено

Коммит `653fa5f` (сторона прогонов, без продуктового кода):

- `scripts/exhaust/probe.ts`: новый `routeReady(hash)` — условие
  «закоммиченный раздел»: `location.hash === hash` И
  `a[href="hash"][aria-current="page"]`. Маркер `aria-current` ставится
  тем же коммитом, что и `#main`, поэтому не может опередить контент.
- Применён во всех навигационных ожиданиях: `sweep.ts` (`navClick` +
  перечисление `first`/`last` через `enumerateAt` + `rescue`),
  `walk-reach.ts goTo`, `trusted.ts restore` (с защитой от пустого hash),
  `run.ts openApp`, `matrix-actions.ts hashWait`, `axis-pass.ts`,
  `envctl.ts` (оба `until` маршрута), `ui-smoke.ts navigate`,
  `ui-smoke-context.ts restoreNavigation`.
- `page-dom.ts`: `waitFor(fn, ms)` — опрос условия с бюджетом, уступающий
  поток рендеру; `routeCommitted(hash)` — страничный аналог `routeReady`.
- `page-sweep.ts`: восстановление маршрута ждёт `routeCommitted` до 500 мс;
  `settleAfter` дожидается поздний коммит до 150 мс после «инертного»
  клика (иначе `opened` терялся → диалог → `dialog-unreachable` →
  `missing`); `reopen` объявляет диалог недоступным только после
  ожидания `dialog#id[open]` до 600 мс.

Коммит `2e8ade5` (дефект продукта):

- `src/demo/modal.tsx`: эффект без зависимостей перевыставляет
  `openDialog(dialog.id)` после каждого коммита, пока DemoModal
  смонтирован и закрыт — DOM всегда согласован с `open:true`.
- `DESIGN.md` (§401): записан контракт «смонтированный DemoModal обязан
  держать dialog открытым».
- `tests/exhaust-waits.test.ts`: 4 поведенческих теста — контракт
  `routeReady` (требует hash + aria-current, не h1), все навигационные
  ожидания используют метку коммита, внутристраничный обход ждёт
  `routeCommitted`/`openDialogs`/`settleAfter`, DemoModal перевыставляет
  open вне эффекта монтирования. На исходном коде тесты не проходят
  (нет `routeReady`, `aria-current`, `waitFor`, второго `openDialog`).

Ничего не ослаблено: порог пропусков `0.4`, лимиты файлов/функций,
таймауты задач и реестры не тронуты; сбросов базлайна нет.
