# Product readiness

Аудит отвечает на вопрос пользователя о готовности продукта; локальный план
не подменяет его замысел. Пакет переносим между Claude Code и Codex: используй
доступные в среде навыки и инструменты, инструкции пользователя имеют приоритет.

## Контракт работы

1. **Бриф.** Запиши цель, аудиторию, сценарии, границу прототипа и критерии
   приёмки из запроса и первичных документов. Покажи расхождения со спецификацией.
   Недостающий существенный выбор уточняй; уже заданную область не сужай.
2. **Исходная фиксация до исправлений.** Сохрани перечень отслеживаемых,
   неотслеживаемых и игнорируемых файлов, состояние рабочей копии, версию,
   доступные команды и доказательства. Не откатывай чужую работу. Если есть
   бэклог, прочитай его инструкции и продолжи найденную задачу вместо дубликата.
3. **Матрица покрытия.** Для каждого требования укажи сценарий, ожидаемый
   результат, источник, наблюдение/артефакт, статус, зависимость и следующий шаг.
   Макет освобождён от настоящих API и хранения, но обещанные действия,
   состояния, языки и диалоги проверяются на демонстрационном результате.
4. **Проверка областей.** Продукт: полнота и понятность сценариев. Архитектура:
   поток данных, границы модулей, сложность и лишние слои. Репозиторий: реальные
   команды проверок, безопасность, назначение каталогов, мёртвые файлы,
   строковые ссылки на пути, актуальность документации и имеющаяся CI.
   Недостающую инфраструктуру не создавай ради аудита.
5. **UI, если он есть.** Проведи три независимые проверки: визуальная иерархия;
   сценарии и понятность; доступность и правила веб-интерфейса. При доступном
   делегировании дай каждому один участок и одинаковый бриф, затем сведи
   находки один раз. Без делегирования выполни раздельные проходы и обозначь
   ограничение независимости. Проверяй мобильную/широкую ширину, клавиатуру,
   фокус, подписи, контраст, ошибки и следствие каждого действия. Соблюдай
   локальный выбор браузера; изолируй сессии и общие ресурсы.
6. **Одна консолидация и одно финальное состязательное ревью.** Сначала объедини
   дубликаты. В единственном финальном ревью проверь находки против исходных
   требований, фактического состояния, доказательств и контраргументов, включая
   организацию репозитория. После исправлений повторяй затронутые проверки
   внутри этого же обзора. Исправления выполняй только в разрешённой области;
   повторное разрешение на уже порученную работу не требуется.

## Статусы и зависимости

| Статус  | Основание                                                                |
| ------- | ------------------------------------------------------------------------ |
| PASS    | Ожидаемое следствие наблюдено; указан воспроизводимый артефакт.          |
| FAIL    | Требование нарушено; есть воспроизведение и влияние.                     |
| UNKNOWN | Не запускалось, результат неизвестен или доказательств недостаточно.     |
| BLOCKED | Названа реальная зависимость, проверенная недоступность и следующий шаг. |
| N/A     | Требование неприменимо по согласованной области, с причиной.             |

Недоступный браузер — BLOCKED/UNKNOWN, а не N/A. STOP означает остановку лишь
зависимого действия при реальном препятствии; независимые проверки продолжаются.
Успешные тесты и линтеры подтверждают свои проверки, а не полноту продукта.
Новички и возрастные группы: экспертная гипотеза отделяется от результатов
испытаний с представителями аудитории.

## Условная маршрутизация

Загружай только подходящие доступные навыки; имена могут иметь префикс пакета.
Явно названный пользователем навык проверь и укажи роль или неприменимость.
Отсутствие необязательного навыка компенсируй прямой проверкой; для необходимой
возможности укажи BLOCKED и причину. Не устанавливай зависимости автоматически.

| Условие                                 | Навык и роль                                                            |
| --------------------------------------- | ----------------------------------------------------------------------- |
| Неясный измеримый результат             | `define-goal`; инструмент цели — только по запросу.                     |
| Новый дизайн/изменение поведения        | `brainstorming`; сначала бриф.                                          |
| Существенная нерешённая развилка        | `grilling`; проверка предпосылок.                                       |
| UI                                      | `frontend-design`, `ui-ux-pro-max`, `web-design-guidelines`: три линзы. |
| Архитектура                             | `codebase-design`; `improve-codebase-architecture`, если доступен.      |
| Первичные источники                     | `research`; меняющиеся факты проверяй на текущую дату.                  |
| Сравнение кода с требованиями/правилами | `code-review`; часть общей консолидации.                                |
| Финальная независимая проверка          | `requesting-code-review`; один общий обзор.                             |
| Организация процесса                    | `using-superpowers`; только применимые этапы.                           |
| Заявленный сбой сессии Superpowers      | `diagnosing-superpowers`; отдельная диагностика.                        |
| Выбор минимального исправления          | `ponytail`; готовое решение, затем собственный код.                     |

Сначала штатные средства платформы и установленные инструменты. Исследования
опираются на первоисточники; укажи дату, ссылку и границу выводов. Недоступный
источник даёт UNKNOWN, предположение подписывается как предположение.

## Результат

Краткий ответ сохраняет четыре поля: файлы и состояние рабочей копии;
три UI линзы и консолидация (либо N/A с причиной); зависимости и ограничения;
одно финальное ревью. Для отсутствующей зависимости укажи «не обнаружена».

Отчёт содержит: вердикт по заявленной цели; исходную фиксацию; матрицу покрытия;
приоритетные находки с воспроизведением и влиянием; точные результаты команд;
использованные/условные/N/A навыки и причины; итог единственного ревью;
зависимости, следующие шаги и остаточные ограничения. Сохрани полезные знания
и существенные решения там, где требуют инструкции проекта.

Пример строки: «Сохранить диалог → демонстрационное подтверждение → UNKNOWN:
нажатие возвращало unknown; нужен повтор с наблюдением DOM». Зелёная сборка
эту строку не меняет. Закрой только собственные временные процессы и сессии,
сохрани доказательства и явно передай недоставленные результаты.
